작성: UX / 대상: dev
근거: `outputs/provider_comparison.txt` (1,024장 = 16종 × 8변형 × 8조건, 2026-08-14)
대상 화면: `web/seller/sell.html` `#stepResult`, `web/js/seller-sell.js` `renderResult()`
관련 코드: `src/ai/providers/heuristic.ts`, `src/ai/providers/cnn.ts`

## 0. 한 줄 결론

**숫자 퍼센트를 화면에서 없앤다.** 대신 "이 품목을 우리가 실제로 몇 번 맞혔는지"를 근거로 한
**3단계 말맛**을 쓰고, 단계에 따라 화면 구성 자체를 바꾼다.
숫자는 지우는 게 아니라 **`근거 보기`를 펼쳤을 때 실측표로** 보여준다.

---

## 1. 문제의 정확한 형태 — "45%"는 평균의 거짓말이다

전체 45%라는 숫자만 보면 "동전 던지기보다 조금 나은 앱"이지만, 품목별로 보면 전혀 다르다.

| 품목 | heuristic 1순위 적중률(전 조건, n=64) |
|---|---|
| 감자 · 양파 | 100% |
| 고구마 | 94% |
| 배 · 감귤 | 88% |
| 건고추 | 86% |
| 복숭아 | 84% |
| 사과 | 75% |
| 쌀 · 마늘 · 포도 · 감 · 고등어 · 새우 · 오징어 · 전복 | **0%** |

즉 실측 분포는 **양극단(8품목 75~100%, 8품목 0%)** 이고, 중간이 거의 없다.
45%는 이 두 무리를 섞은 평균일 뿐이며, 화면이 말해야 할 숫자가 아니다.

**그래서 설계 원칙:**
> 화면은 "AI 일반의 정확도"가 아니라 **"지금 이 품목을, 지금 이 사진 상태에서 우리가 얼마나 맞혀 봤는지"** 를 말한다.

이 접근은 이미 코드에 선례가 있다. `cnn.ts` 의 `gradeIsUsable()` 은
"전체 평균은 통과하지만 양파는 못 넘는다"는 이유로 **per_item 근거를 평균보다 먼저** 본다.
신뢰도 표시도 같은 규칙을 쓴다.

## 2. 질문별 답

### Q1. 숫자 퍼센트를 계속 보여줘야 하는가 → **아니다. 기본 화면에서는 제거.**

세 가지 이유:

1. **읽히지 않는다.** 어르신 사용자에게 "78%"는 행동을 바꾸지 못한다. 78%와 62% 사이에서
   무엇을 다르게 해야 하는지 화면이 알려주지 않기 때문이다. 퍼센트는 *판단을 사용자에게 떠넘기는*
   표시다. 우리 원칙("AI는 판매를 돕기만 한다")은 판단을 떠넘기라는 뜻이 아니라
   **최종 선택권을 남긴다**는 뜻이다. 이 둘은 다르다.
2. **의미가 없다.** 현재 `confidence` 는 색 매칭 확률 × 신호품질이지, "맞을 확률"로 보정
   (calibration)된 값이 아니다. 실측상 heuristic 이 **틀렸을 때의 평균 신뢰도가 0.32~0.38**,
   맞았을 때와 겹친다. 즉 이 숫자는 맞고 틀림을 구분하지 못한다. 구분 못 하는 숫자를 소수점까지
   보여주는 것은 정밀함의 연출일 뿐이다.
3. **CNN 쪽은 더 위험하다.** `capConfidence` 의 상한이 `val_object_level.item = 1.0` 이라
   아무것도 자르지 않는다. 틀렸을 때 평균 신뢰도가 0.50~0.71이므로,
   **"확신에 차서 틀리는" 화면**이 만들어진다. 이건 UX 문제 이전에 사고다.

**대체물:** 퍼센트 대신 (a) 3단계 말맛, (b) 화면 구성의 변화, (c) 접어둔 `근거 보기`.

### Q2. 정직함과 사용성을 동시에 잡는 법 → **평균을 고백하지 말고, 품목별로 말하라.**

"이 앱의 정확도는 45%입니다"라고 쓰면 아무도 안 쓴다. 그리고 그건 **부정확하기까지 하다** — 감자는 100%다.
정직함의 올바른 단위는 앱이 아니라 **품목 × 촬영조건**이다.

- 감자 사진 → "감자 같아요" (강하게 제안해도 실측이 뒷받침한다)
- 전복 사진 → "사진으로는 잘 모르겠어요. 직접 골라 주세요" (0%인 품목에서 추측을 내밀지 않는다)

이렇게 하면 사용자가 겪는 체감 정확도는 45%가 아니라
**"AI가 말을 걸었을 때는 대체로 맞고, 모르면 솔직히 모른다고 한다"** 가 된다.
불신은 낮은 정확도에서 오지 않고 **틀린 확신**에서 온다. 우리가 없앨 것은 후자다.

추가로, 실패해도 사용자가 손해 보지 않는다는 사실을 화면이 계속 상기시킨다:

> "고르신 대로 등록됩니다. AI는 가격도 등급도 정하지 않아요."

이 한 줄이 정확도 논쟁 자체의 무게를 줄인다. 틀려도 되는 구조라는 걸 알면 45%도 감당 가능하다.

## 3. 신뢰 단계 — 3단계로 확정

4단계 이상은 어르신 화면에서 구분되지 않는다(말맛 차이를 못 느낌). 2단계는 "모르겠음"을 못 담는다.
**3단계**로 간다.

| 단계 | 코드값 | 1순위 문구(화면 h1) | 보조 문구 | 뜻 |
|---|---|---|---|---|
| A | `likely` | **"감자 같아요"** | "맞으면 눌러 주세요" | 이 품목을 여러 번 맞혀 봤고, 사진 상태도 좋다 |
| B | `unsure` | **"혹시 사과인가요?"** | "아니면 아래에서 골라 주세요" | 맞혀 본 품목이지만, 사진 상태가 나쁘거나 후보가 접전이다 |
| C | `unknown` | **"사진으로는 잘 모르겠어요"** | "무엇을 파실지 직접 골라 주세요" | 실측 0%이거나 미측정 품목 / 후보 없음 |

말맛 규칙:
- **A는 평서형, B는 의문형, C는 고백형.** 문장 종결어미만으로 확신도가 전달되게 한다. 아이콘·색으로
  단계를 구분하지 않는다(색은 이미 `--brand` 하나로 제한).
- "정확도", "신뢰도", "확률", "AI 판정" 같은 단어를 1순위 문구에 쓰지 않는다.
- TTS(`speakCandidates`)도 같은 문장을 그대로 읽는다. 화면과 음성이 다른 말을 하면 안 된다.
  - A: "감자 같습니다. 맞으면 눌러 주세요. 아니면 일번 고구마, 이번 양파 중에 골라 주세요."
  - C: "사진으로는 잘 모르겠습니다. 무엇을 파실지 직접 골라 주세요."

### 3-1. 단계 판정 규칙 (서버 계산, 화면은 받아쓰기만)

`RecognitionResult` 에 필드 하나를 추가한다. **화면에서 임계값을 계산하지 않는다** — 근거가 코드
한 곳에 모여 있어야 심사·유지보수 때 답할 수 있다.

```ts
// src/ai/confidence-tier.ts (신규)
export type ConfidenceTier = 'likely' | 'unsure' | 'unknown';

export interface TierResult {
  tier: ConfidenceTier;
  measured_hit_rate: number | null; // 이 품목 실측 1순위 적중률(0~1). 미측정이면 null
  sample_n: number | null;          // 실측 표본 수
  reason: string;                   // 화면 '근거 보기'에 그대로 출력
}
```

판정 순서:

1. 후보가 없거나 `product === ''` → **C**
2. 해당 품목의 **실측 적중률 표**(3-2)를 조회
   - 표에 없음(미측정) → **C**, reason `"이 품목은 아직 시험해 보지 못했습니다"`
   - 적중률 `< 0.30` → **C**, reason `"이 품목은 사진으로 맞힌 적이 거의 없습니다 (n/64회 중 m회)"`
   - 적중률 `>= 0.70` → 3번으로
   - 그 사이(0.30~0.70) → **B**
3. 사진 신호 품질(`quality.signalQuality`) 및 감점 조건 확인
   - `signalQuality < 0.5` 이거나 `detected_issues` 가 1개 이상 → **B**로 강등
     (실측상 '흙·상자 배경'에서 heuristic 은 50%→16%로 무너진다 — `provider_comparison.txt`
      조건별 표, A·B 두 축소 방식 모두 동일. 배경이 지저분하면 등급을 내려야 한다)
   - ~~1순위와 2순위 확률 차가 `< 0.10` (접전) → **B**로 강등~~
     **[2026-08-14 dev 측정 후 삭제]** 이 규칙은 유효성이 확인되지 않았다.
     A 후보 8품목(n=512)에서 접전/비접전 적중률은 임계값에 따라 방향이 뒤집힌다:
     0.05 → 91.7% vs 89.1%(접전이 오히려 높음), 0.10 → 83.7% vs 93.7%, 0.15 → 88.7% vs 92.8%.
     품목 안에서 보면 방향이 일치하지 않는다(배 접전 100% vs 비접전 0%, 감자·양파는 차이 없음,
     복숭아만 강하게 지지). 유효 독립표본이 품목 8개뿐이라 0.10 에서의 -10p 는 임계값을 고른 결과다.
     무엇보다 이 규칙은 `confidence_calibration.txt` 가 "정보 없음"을 증명한 바로 그 confidence
     숫자에 다시 기대고 있다. 그래서 코드에 넣지 않았다(사유는 `confidence-tier.ts` 주석에도 있음).
   - 그 외 → **A**
4. 프로바이더가 CNN이고 해당 품목이 **모델 미학습 5종 밖**이면 무조건 **C**
   (원리적으로 0%인 품목에 대해 확률을 만들어내는 것을 화면 앞에서 차단)

> A로 올라가는 길은 좁고, C로 떨어지는 길은 넓다. 의도된 비대칭이다. 틀린 확신의 비용이
> "모르겠다"의 비용보다 훨씬 크기 때문이다.

### 3-1-a. [2026-08-14 dev 측정] 판정 기준을 재현율 → **정밀도**로 바꿨다

설계서 3-2 의 표는 **재현율**(진짜 감자 사진을 감자로 맞힌 비율)이다. 그런데 화면이 하는 말은
"감자 같아요" 이고, 그 문장이 맞을 확률은 **정밀도**(감자라고 말했을 때 실제 감자였던 비율)다.
같은 1,024장에서 둘을 따로 재 보면:

| 예측 품목 | 판정 횟수 | 그중 실제로 맞음 | **정밀도** | (참고)재현율 |
|---|---|---|---|---|
| 복숭아 | 54 | 54 | **100%** | 84% |
| 사과 | 49 | 48 | **98%** | 75% |
| 건고추 | 63 | 55 | **87%** | 86% |
| 고구마 | 116 | 60 | **52%** | 94% |
| 감귤 | 112 | 56 | **50%** | 88% |
| 배 | 114 | 56 | **49%** | 88% |
| 양파 | 160 | 64 | **40%** | 100% |
| 감자 | 356 | 64 | **18%** | 100% |

**재현율로 판정하면 어휘 밖 게이트가 한 번도 작동하지 않는다.** heuristic 은 색표에 있는 8품목만
출력할 수 있어서, 0%인 8품목(쌀·마늘·포도·감·고등어·새우·오징어·전복)은 애초에 판정 결과로
나오지 않는다. 실제로 일어나는 일은 그 반대다 — **전복 사진을 넣으면 '감자'로 판정된다.**
감자의 재현율은 100%이므로 재현율 기준으로는 A등급이 되어 "감자 같아요"가 뜬다.
브라우저로 재현해 확인한 사실이다.

정밀도로 판정하면 감자(18%)가 C로 떨어지고, 전복 사진은 `stepManual` 로 직행한다.
즉 **"0% 품목에 추측을 내밀지 않는다"는 목표를 실제로 달성하는 유일한 기준이 정밀도**다.
CNN 도 같다(감귤 정밀도 18.6%, 양파 20.9%, 감자 24.9%, 사과 69.6%, 배 98.2%).

`measured-accuracy.json` 에는 두 값을 모두 적되, 단계 판정은 정밀도만 본다.
재현율은 `근거 보기` 용 참고값이다.

### 3-2. 실측 적중률 표 (하드코딩 금지 — 데이터 파일로)

`src/ai/measured-accuracy.json` 을 만들고 `provider_comparison.txt` 의 **B 섹션(NEAREST 축소,
실제 폰 입력에 가까움)** 값을 넣는다. A 섹션이 아니라 B 섹션을 쓰는 이유: 브라우저 캔버스 축소가
실제 사용자 입력 경로이므로, 더 보수적이고 더 현실적인 쪽을 채택한다.

```json

    "heuristic 색표는 이 시험 사진들로 맞춘 값이라 heuristic 에게 유리한 시험지다",
    "실제 휴대폰으로 찍은 사진 표본은 0장이다"

    "peach": 0.84, "apple": 0.75,

```

- 품목 코드는 카탈로그 코드와 정확히 일치시킬 것(dev: 실제 코드값 확인 후 반영).

  설계서 `dried_pepper` → 실제 카탈로그 코드는 **`red_pepper`** (seed.ts). 이 코드로 반영했다.
- 이 표는 **재측정 시 이 파일만 갈아끼우면 화면 문구가 따라 바뀌도록** 설계한다. 로직에 숫자를 박지 않는다.

### 3-3. 프로바이더 쪽 함께 고칠 것

- `heuristic.ts` `MAX_CONFIDENCE = 0.86` → 화면에서 퍼센트를 안 쓰므로 표시용으로는 무의미해지지만,
  내부 정렬용 값이므로 **그대로 둔다**. 단, 이 값이 "정확도"가 아니라 "정렬용 점수"임을 주석에 명시.
- `cnn.ts` `capConfidence` — **[dev 변경]** `Math.min(ceiling, 0.9)` 대신,
  metadata 의 측정 기록(`val_object_level.item = 1.0`)은 **그대로 두고** 실전 상한을
  `field_ceiling`(기본 0.74) 이라는 **별도 필드**로 두어 둘 중 작은 값을 쓴다.
  1.0 은 '검증셋에서 실제로 측정된 값'이라 임의로 낮춰 적으면 측정 기록이 훼손되기 때문이다.
  0.74 는 학습 5품목 CNN(TTA켬) top-1 적중률 0.74~0.95 중 보수적인 쪽이다.
- `heuristic.ts` `MAX_CONFIDENCE = 0.86` 은 남긴다. 다만 관측 최댓값이 0.461 이라 한 번도 걸리지
  않았다는 사실과, 프로토타입 표가 바뀔 때를 대비한 마지막 방어선이라는 점을 주석에 적었다.

## 4. 단계별 화면 구성 — 문구만 바꾸는 게 아니라 화면이 달라진다

### 4-A. `likely` — 지금과 가장 비슷하되 1순위를 크게

```
어느 것인가요?                       ← h1 을 "감자 같아요" 로 교체
──────────────────────────────
┌────────────────────────────┐
│  [사진]  감자                │  ← 1순위 카드: 높이 1.4배, --brand 테두리
│          맞으면 눌러 주세요    │
└────────────────────────────┘
  다른 것이라면                        ← 작은 라벨
  [ 2 고구마 ]  [ 3 양파 ]            ← 2·3순위 나란히, 기본 크기
──────────────────────────────
  [AI 확인] [사진 상태: 좋음]  근거 보기 ›
  여기 없어요 · 직접 고르기
  사진 다시 찍기
```

- 1순위 카드 안의 `.cf` 문구: `"가장 비슷해요"` → **`"이 사진에서는 감자로 보입니다"`**
- 2·3순위 `.cf`: `"비슷할 수 있어요"` → **`"이것일 수도 있어요"`** (현행 유지 수준, 톤만 부드럽게)

### 4-B. `unsure` — 후보를 **동등하게** 늘어놓는다

```
혹시 사과인가요?
아니면 아래에서 골라 주세요.
──────────────────────────────
[ 1 사과 ] [ 2 배 ] [ 3 복숭아 ] [ 4 감 ]   ← 전부 같은 크기, 1순위 강조 제거
──────────────────────────────
  왜 자신이 없나요?  › (펼침)
    · 사진 배경에 흙과 상자가 같이 보여요
    · 사과와 배가 색으로는 비슷합니다
──────────────────────────────
  [ 전체 목록에서 고르기 ]      ← ghost 가 아니라 일반 버튼으로 승격
  사진 다시 찍기
```

핵심 변경 3가지:
1. **1순위 시각 강조(`.cand.on`)를 뺀다.** 자신 없으면서 첫 칸만 크게 그리면 말과 화면이 어긋난다.
2. **후보를 3개 → 최대 4개로 늘린다.** 접전일 때 답이 4번째에 있을 수 있다.
3. **`전체 목록에서 고르기`를 ghost → 일반 버튼으로 승격**하고 후보 바로 아래로 올린다.
   지금은 `#resultNo` 가 `.s-foot` 안 ghost라 "실패했을 때 누르는 버튼"처럼 보인다.
   B단계에서는 이게 **정상 경로**다.

### 4-C. `unknown` — AI 후보를 아예 내밀지 않는다

```
사진으로는 잘 모르겠어요
무엇을 파실지 직접 골라 주세요.
──────────────────────────────
[ 사과 ] [ 배 ] [ 감 ] [ 포도 ]
[ 감귤 ] [ 복숭아 ] [ 쌀 ] [ 마늘 ]
      … 전체 품목 그리드 …
──────────────────────────────
  사진은 그대로 쓰입니다. 다시 찍지 않으셔도 돼요.
  왜 모르나요? ›
    이 품목은 아직 사진으로 시험해 보지 못했습니다.
    (전복 · 시험 표본 없음)
  사진 다시 찍기
```

- 사실상 `stepManual` 화면을 그대로 쓴다. **`stepResult` 를 건너뛰고 `stepManual` 로 직행**하되,
  `stepManual` 상단에 "사진으로는 잘 모르겠어요 / 왜 모르나요" 블록을 얹는다.
- **"사진은 그대로 쓰입니다"** 문구가 중요하다. 어르신은 AI가 실패하면 사진도 날아갔다고 생각한다.
  실제로는 `state.pendingImage` 로 유지되므로, 그 사실을 말해 준다.
- 0%인 8품목(쌀·마늘·포도·감·고등어·새우·오징어·전복)은 이 경로로만 등록된다.
  **틀린 추측을 한 번도 내밀지 않는 것**이 이 설계의 가장 큰 실익이다.

## 5. 배지 재정리 — 지금 3개는 서로 겹친다

현재 `#stepResult` 의 배지 3개:

| 현재 | 문제 | 조치 |
|---|---|---|
| `#badgeSource` "AI 확인" | 프로바이더 이름/오프라인 여부 | **유지** (오프라인 표기는 신뢰 자산) |
| `#badgeQuality` "AI 품질 참고: ○○" | "품질"이 **사진 품질**인지 **농산물 등급**인지 모호. 어르신은 등급으로 읽는다 | **문구 교체**: `사진 상태: 좋음 / 보통 / 어두움` — 주어를 사진으로 못 박는다 |
| `#badgeConfidence` "1순위 신뢰도 78%" | 본 문서의 문제 그 자체 | **제거.** 자리에 `근거 보기 ›` 링크 |

배지 줄 최종:

```html
<div class="badge-row">
  <span class="badge badge-ai" id="badgeSource">AI 확인 · 사진 외부 전송 없음</span>
  <span class="badge badge-hint" id="badgePhoto">사진 상태: 좋음</span>
  <button class="link-basis" id="basisToggle" type="button" aria-expanded="false">근거 보기 ›</button>
</div>
```

- `badge-muted` 스타일은 다른 화면에서 쓰이면 남기고, 이 화면에서만 뺀다.
- "AI 품질 참고"라는 말은 **전 화면에서 폐기**한다. 등급 오해 소지가 있고,
  "AI는 등급을 확정하지 않는다"는 원칙과 정면으로 헷갈린다.

### 5-1. 검수 타임라인과의 정합

검수 타임라인은 "사람이 확인한다"는 서사다. 신뢰 단계는 그 서사의 **앞단**이다. 문구를 이어 붙인다:

- A/B단계 확인 화면 하단 고정 문구:
  > "고르신 내용으로 등록됩니다. 가격과 등급은 AI가 정하지 않고, 검수에서 사람이 확인합니다."
- C단계에서도 같은 문구를 쓴다. 즉 **AI가 맞히든 못 맞히든 뒤에 사람이 있다**는 사실이 상수로 유지된다.
  이게 45%를 감당 가능하게 만드는 구조적 장치다.

## 6. 안내 모드(`data-guide='on'`)와의 결합

`docs/판매안내모드-설계.md` 규칙에 따라 **안내 모드는 얹기만 한다.**

| 상태 | 안내 ON 추가 요소 | 안내 OFF |
|---|---|---|
| A | 1순위 카드에 `.is-guided` 펄스 1개 | 없음 |
| B | 후보 그리드 위 한 줄: "천천히 보시고 고르세요. 없으면 아래 전체 목록을 눌러 주세요." | 없음 |
| C | 전체 그리드 위 한 줄: "이건 AI가 어려워하는 품목이에요. 직접 골라 주시면 됩니다." | 없음 |

- 강조는 화면당 하나 원칙 유지 — B·C에서는 펄스를 쓰지 않는다(강조 대상이 그리드 전체라 강조가 안 됨).
- `근거 보기`는 안내 모드와 무관하게 항상 접힌 상태로 존재한다.

## 7. `근거 보기` — 심사위원 질문에 화면이 직접 답하는 부분

`basisToggle` 을 누르면 펼쳐지는 블록. **접혀 있으므로 어르신 사용을 방해하지 않고,
펼치면 심사 답변이 된다.** 이 이중 목적이 이 컴포넌트의 존재 이유다.

```
근거 보기 ▾
──────────────────────────────────────────────
이 사진에서 본 것
  · 붉은 계열 색이 넓게 분포 / 둥근 형태
  · 확인 어려웠던 점: 배경에 상자

이 품목을 우리가 얼마나 맞혔나
  감자 — 64번 시험해서 64번 맞혔습니다 (100%)
  시험 조건: 밝은 곳 · 어두운 곳 · 멀리서 · 기울여서 등 8가지

시험의 한계 (숨기지 않습니다)
  · 시험 사진 1,024장은 상품 사진을 변형해 만든 것입니다.
  · 지금 방식(색 기준)은 이 사진들에 맞춰 조정돼 있어, 실제보다 유리하게 나올 수 있습니다.
  · 실제 휴대폰으로 찍은 사진으로는 아직 시험하지 못했습니다. (표본 0장)

측정일 2026-08-14 · 표본 1,024장 (16품목 × 8변형 × 8조건)
```

**규칙:**
- 마지막 "시험의 한계" 세 줄은 **A/B/C 모든 단계에서 항상 노출**한다. 조건부로 숨기지 않는다.
  실측 한계를 화면이 스스로 말하게 하는 것이 이 설계의 정직성 담보다.
- 문구는 `measured-accuracy.json` 의 `caveats` 배열에서 렌더한다. 데이터와 화면이 어긋나지 않게.
- `field_evaluated: false` 인 동안에는 "실제 휴대폰 사진 표본 0장" 줄을 **강제 표시**하고,
  `true` 로 바뀌면 자동으로 실측 문구로 교체되게 한다.
- 0% 품목에서는 "64번 시험해서 0번 맞혔습니다"라고 그대로 쓴다. 이 문장이 C단계의 정당성이다.

심사위원 대응 관점에서 이 블록이 답하는 것:
1. "수치 근거가 뭐냐" → 측정일·표본 수·조건 8종이 화면에 있다.
2. "과적합 아니냐" → 우리가 먼저 "유리하게 나올 수 있다"고 써 놨다.
3. "실사용 검증했냐" → "표본 0장"이라고 화면이 말한다. 지적당하는 게 아니라 **먼저 공개한** 것이 된다.

## 9. 검증 기준 (QA에게)

1. 0% 품목 8종 사진으로 등록 시도 → **AI 후보가 단 한 번도 뜨지 않아야** 한다.
2. 감자·양파 사진 → A단계, 1순위 강조, 문구 "감자 같아요".
3. 흙·상자 배경 사진 → 품목이 감자여도 **B로 강등**되어야 한다.
4. 화면 어디에도 `%` 문자가 남아 있지 않다(`근거 보기` 내부는 예외).
5. `근거 보기`를 펼치면 A/B/C 모든 경우에 "표본 0장" 한계 문구가 보인다.
6. 밀도토글 '작게/크게' 양쪽에서 B·C 그리드가 줄바꿈 깨지지 않는다.
7. TTS가 읽는 문장과 h1 문장이 글자 단위로 같다.
